# CAD Support

ระบบรับแจ้งปัญหาและคำขอแก้ไขสำหรับหลายสหกรณ์ มีหน้ารับแจ้งทั่วไปและพื้นที่เจ้าหน้าที่แยกกัน

## เริ่มใช้งาน

1. ผู้ดูแลเปิด `/manage` และลงชื่อเข้าใช้ด้วยบัญชี ChatGPT ที่ได้รับสิทธิ์
2. เปิด **ทะเบียนสหกรณ์** เพิ่มสหกรณ์เอง หรือนำเข้า Excel (.xlsx) จากไฟล์ตัวอย่างในระบบ
3. ตรวจสอบผู้ติดต่อกับสหกรณ์ก่อนอนุมัติ ผู้ติดต่อที่นำเข้าใหม่มีสถานะรออนุมัติเสมอ
4. เปิดแท็บ **ลิงก์และ QR Code** เพื่อคัดลอกลิงก์กลางหรือสร้างลิงก์เฉพาะสหกรณ์ แล้วส่งผ่าน LINE ตามช่องทางที่ใช้จริง
5. ตั้งค่า Supabase Auth และบริการส่งอีเมลตาม `docs/email-setup.md` เพื่อเปิดการรับลิงก์อีเมลจริง

ทะเบียนจริงเริ่มว่าง ไม่มีการนำข้อมูลตัวอย่างหรือข้อมูลทดสอบขึ้นโฮสต์ ต้องเพิ่มหรือนำเข้าทะเบียนก่อนสหกรณ์เริ่มแจ้งเรื่องได้

## วิธีรับเรื่องและสิทธิ์

| ผู้ใช้ | สิทธิ์ |
| --- | --- |
| ผู้แจ้งทั่วไป | เลือกสหกรณ์ที่เปิดรับเรื่อง ส่งปัญหาและไฟล์แนบ รับเฉพาะเลขอ้างอิง ไม่อ่านประวัติหรือไฟล์ได้ |
| ผู้ติดต่อที่ได้รับอนุมัติ | ยืนยันอีเมลแล้วดูเรื่องและดาวน์โหลดไฟล์ของสหกรณ์ที่ได้รับสิทธิ์ เพิ่มความคิดเห็น และส่งคำขอแก้ไขได้ |
| เจ้าหน้าที่รับเรื่อง | เข้าผ่าน ChatGPT ดูและจัดการงานทั้งหมด กำหนดสถานะและผู้รับผิดชอบ แต่อนุมัติสมาชิกหรือคำขอแก้ไขไม่ได้ |
| ผู้ดูแลระบบ | จัดการทะเบียน สิทธิ์เจ้าหน้าที่ อนุมัติผู้ติดต่อ และอนุมัติ/ไม่อนุมัติคำขอแก้ไข |

การพิมพ์ชื่อหรือเลือกสหกรณ์ในแบบฟอร์มไม่ให้สิทธิ์อ่านข้อมูล การรับเรื่องทั่วไปไม่ได้ยืนยันอีเมลผู้แจ้ง ทุก API และไฟล์แนบตรวจสิทธิ์ฝั่งเซิร์ฟเวอร์ เลขอ้างอิงเพียงอย่างเดียวใช้เปิดรายละเอียดไม่ได้

เจ้าหน้าที่ใช้ระบบเข้าสู่ระบบของ Sites / ChatGPT ผู้ติดต่อใช้อีเมลผ่าน Supabase Auth หรือใช้บัญชี ChatGPT ที่ตรงกับอีเมลที่ได้รับอนุมัติได้ หลักฐานยืนยันอีเมลจาก Supabase ให้สิทธิ์ผู้ติดต่อเท่านั้น ไม่ให้สิทธิ์เจ้าหน้าที่ แม้อีเมลตรงกับผู้ดูแล

## โปรแกรมและการทำงาน

- โปรแกรม: ระบบบัญชีแยกประเภท ระบบเงินรับฝาก ระบบสินค้า ระบบสมาชิกและหุ้น
- ประเภทเรื่อง: แจ้งปัญหา / ขอแก้ไข
- คำขอแก้ไขใหม่ต้องมีผู้ติดต่อที่ได้รับสิทธิ์ และรอผู้ดูแลอนุมัติก่อนเริ่มดำเนินการ ไม่อนุมัติต้องระบุเหตุผล
- ไฟล์ PNG/JPG/WEBP/PDF ไม่เกิน 3 ไฟล์ ไฟล์ละ 5 MB เก็บใน R2 การดาวน์โหลดตรวจสิทธิ์สหกรณ์ทุกครั้ง
- สถานะ ผู้รับผิดชอบ ความคิดเห็น และผลอนุมัติมีประวัติการเปลี่ยนแปลง พร้อมป้องกันการแก้ไขทับรุ่นข้อมูลเก่า
- ค้นหาและกรองตามสหกรณ์ โปรแกรม ประเภทเรื่อง การอนุมัติ ความเร่งด่วน และสถานะ ส่งออก CSV ได้ตามสิทธิ์
- รายงานแนวโน้มและสรุปแยกโปรแกรม / ประเภทเรื่อง / ความเร่งด่วน
- รายการเก่าที่ไม่มีสหกรณ์ยังคงอยู่และเห็นได้เฉพาะเจ้าหน้าที่
- การระงับผู้ติดต่อหรือสหกรณ์มีผลต่อ API ครั้งถัดไปทันที

ระบบนี้ไม่เชื่อมฐานข้อมูลบัญชีของกรมฯ และไม่ได้แก้ไขข้อมูลบัญชีให้อัตโนมัติ ไม่มีการส่ง LINE หรืออีเมลแจ้งเตือนงานอัตโนมัติ การส่งลิงก์รับเรื่องทำผ่านผู้ใช้งาน ส่วนอีเมลสำหรับเข้าสู่ระบบใช้บริการภายนอกที่ต้องตั้งค่าก่อน

## นำเข้า Excel

หัวตาราง: `รหัสสหกรณ์`, `ชื่อสหกรณ์`, `จังหวัด`, `ชื่อผู้ติดต่อ`, `อีเมล`, `โทรศัพท์`

รหัสและชื่อต้องมีทุกแถว อีกสี่ช่องเป็นข้อมูลเสริม หากระบุอีเมลต้องมีชื่อผู้ติดต่อ รหัสซ้ำในไฟล์ต้องมีชื่อและจังหวัดตรงกัน สามารถมีหลายแถวต่อสหกรณ์เพื่อเพิ่มผู้ติดต่อหลายคน ไฟล์รองรับสูงสุด 5 MB และ 5,000 แถว ตรวจตัวอย่างก่อนยืนยัน บันทึกครั้งละไม่เกิน 500 แถว แต่ละชุดบันทึกแบบ atomic หากชุดหลังล้มเหลวจะแสดงจำนวนแถวที่บันทึกไปแล้วและทำต่อได้

รหัสสหกรณ์เดิมปรับเฉพาะชื่อและจังหวัด โดยเก็บ ID สถานะ และสิทธิ์ผู้ติดต่อเดิมไว้ ผู้ติดต่อใหม่รออนุมัติ ผู้ติดต่อเดิมไม่ถูกลดหรือเพิ่มสิทธิ์จากการนำเข้าซ้ำ

## การติดตั้งและฐานข้อมูล

ใช้ Node.js 22.13 ขึ้นไป ติดตั้งด้วย Sites `install-dependencies.mjs` หรือ `npm run install:ci`

`npm run build` สร้าง artifact และ config สำหรับ D1/R2 ใช้ migration ที่ยังไม่ได้ใช้ตามลำดับ (0000, 0001, 0002) ในฐานข้อมูลท้องถิ่น:

```sh
node --import ./scripts/sites-env.mjs ./node_modules/wrangler/bin/wrangler.js d1 execute DB --local --config dist/server/wrangler.json --persist-to .wrangler/state --file drizzle/0002_dizzy_supreme_intelligence.sql
```

เริ่ม `npm run dev` แล้วเข้าที่ URL ที่ปรากฏ ใช้ `/signin-with-chatgpt?return_to=/manage` เพื่อลงชื่อเข้าใช้บัญชีจำลองเฉพาะ localhost ตั้ง `SUPPORT_ADMIN_EMAILS=seedy@sites.test` ใน `.dev.vars` สำหรับพัฒนาเท่านั้น

## ตัวแปรโฮสต์

- `SUPPORT_ADMIN_EMAILS`: อีเมลผู้ดูแลที่ยืนยันผ่าน Sites / ChatGPT คั่นหลายอีเมลด้วย comma กำหนดฝั่งเซิร์ฟเวอร์เท่านั้น ไม่มีการให้ผู้เข้าชมคนแรกเป็นผู้ดูแล
- `PUBLIC_APP_ORIGIN`: origin จริงของเว็บไซต์ ใช้ตรวจ redirect ของการเข้าสู่ระบบ
- `SUPABASE_URL`, `SUPABASE_ANON_KEY`: ตั้งเมื่อต้องการเปิดอีเมลลิงก์ ดูคู่มือประกอบ

ห้ามส่ง `.dev.vars*`, `.env*`, `.wrangler/`, `.sites-runtime/` และ `outputs/` เข้า source control การเผยแพร่ใช้ manifest เดิมและ Sites workflow เพื่อใช้ migration ก่อน deploy

## การทดสอบ

`node node_modules/typescript/bin/tsc --noEmit` และ Sites build ผ่านแล้ว

ทดสอบ browser ผ่าน `node scripts/verify-browser.mjs` หรือ `node scripts/verify-cooperatives.mjs` โดยต้องมี Chrome และ `playwright-core` ตั้ง `PLAYWRIGHT_MODULE_PATH` / `CHROME_PATH` หากอยู่ภายนอกโครงการ

ชุดทดสอบใช้ localhost 5173 และ mock Supabase Auth ที่ 127.0.0.1:8899 เท่านั้น เริ่มด้วย `node scripts/mock-email-auth.mjs` และตั้ง `.dev.vars` สำหรับ QA:

```text
SUPPORT_ADMIN_EMAILS=seedy@sites.test
PUBLIC_APP_ORIGIN=http://127.0.0.1:5173
SUPABASE_URL=http://127.0.0.1:8899
SUPABASE_ANON_KEY=local-qa-only
```

อย่าใช้ค่า QA บนโฮสต์จริง การเชื่อม HTTP localhost ถูกจำกัดให้ใช้ได้เฉพาะเมื่อ origin เป็น localhost ตาม config นี้

ทดสอบการแยกสหกรณ์ ดาวน์โหลดไฟล์ คำขอแก้ไข/อนุมัติ การเพิกถอนสิทธิ์ ทะเบียน Excel/QR ปฏิเสธการปลอม identity การแยกบทบาท การต่ออายุ session และหน้าจอมือถือ ผลการทดสอบอยู่ใน `outputs/cooperative-qa.json`

**ข้อจำกัดการตรวจสอบ:** ลิงก์อีเมลและ refresh ทดสอบกับผู้ให้บริการจำลองในเครื่อง ไม่ใช่การส่งอีเมลจริง ต้องเชื่อม Supabase และตั้ง SMTP แล้วตรวจรับอีเมลจริงก่อนประกาศให้ผู้ติดต่อใช้อีเมลเข้าสู่ระบบ
